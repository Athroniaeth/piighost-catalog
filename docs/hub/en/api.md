# The catalog's HTTP API

Read only, public, under `/api/v1`. This is what the piighost library
and the site consume. The routes do not carry the template's API key: they serve
only what the registry publishes, and a third party has to be able to resolve a
reference from their own deployment. The per-client quota and the body size
limit apply as they do to the rest of the API. The exact contract is
`openapi.json` at the repository root, regenerated by `just types`.

| Route | Returns |
|---|---|
| `GET /api/v1/vocabulary` | the tag vocabulary, with `kind` and labels |
| `GET /api/v1/refs?kind=&tag=` | the object list: key, kind, description, tags, `latest` commit, pointers |
| `GET /api/v1/refs/{ns}/{name}` | one object and the list of its commits |
| `GET /api/v1/refs/{ns}/{name}/{selector}` | one commit: digest, date, frozen content |
| `GET /api/v1/refs/{ns}/{name}/{selector}/resolved` | the resolution: labels and provenance for a pattern or a group, detectors and stages for a configuration, and the rendered pipeline |
| `GET /api/v1/refs/{ns}/{name}/{selector}/pipeline.toml?memory=&keep_refs=` | the piighost pipeline as TOML, `application/toml` |
| `GET /api/v1/refs/{ns}/{name}/{selector}/snippets` | ready-to-paste snippets, one per target |
| `GET /api/v1/search?q=&kind=&tag=&label=&sort=` | the search and the facet counts of its result; `sort` is `relevance`, `updated`, `used`, `labels` or `name` |
| `GET /api/v1/stats?days=` | the registry's usage over a window, aggregated from counters |
| `GET /api/v1/labels` | every label the registry can emit |
| `GET /api/v1/samples` | the annotated texts, with their annotations |
| `GET /api/v1/diff/{ns}/{name}?before=&after=` | what two commits detect differently. No screen on the site, and no command in the library |
| `GET /api/v1/badge/{ns}/{name}?tag=` | a shields.io endpoint, to show a commit in a README. No screen either, by design |

`{selector}` is a tag, `latest` included, or an eight character hexadecimal
commit. The tags of a search combine with AND: ticking two facets narrows, which
is what the counts announce. Every result carries the bilingual description, the
date of the last recorded commit and the number of commits, which is what a row
of the catalog shows.

## Interactive routes

They take a JSON body and return 200: nothing is created, nothing is stored. The
text of a call is neither logged nor kept, since that is precisely the data the
pipeline exists to hide.

| Route | Body | Role |
|---|---|---|
| `POST /api/v1/playground` | `{ref, text}` | runs a registry object over a text |
| `POST /api/v1/playground/candidate` | `{regex, text, label}` | tries a regex that is not in the registry yet |
| `POST /api/v1/playground/chat` | `{ref, messages}` | replays a conversation with a scripted assistant |
| `POST /api/v1/compare` | `{refs, text}` | runs two to four objects over a text and says where they differ |
| `POST /api/v1/submissions/check` | `{kind, namespace, name, manifest}` | validates a manifest and returns a ready pull request |

Two execution paths, because the risk is not the same. A registry pattern has
passed the backtracking bound, so it runs in process, over a text capped at
20,000 characters. A regex typed by a visitor has passed nothing, so it runs in a
subprocess killed after two seconds: that costs a process start and cannot block
the server.

The chat is stateless: the client sends the whole conversation back on every
call, so two workers answer the same and nothing needs storing between requests.
The assistant's reply is scripted, which makes the demo free and reproducible; it
demonstrates the round trip, the restoration and one token per value, which a
real model would not prove any better.

## Caching

Every selected response carries `ETag: "<full digest>"`. A selector that is a
commit returns `Cache-Control: public, max-age=31536000, immutable`, because that
content will never change. A tag returns `Cache-Control: public, no-cache`: the
client may keep the response but has to revalidate it, since the tag may have
moved.

## Errors

Body is `application/problem+json`.

| Code | When |
|---|---|
| 400 | a namespace, a name or a selector does not follow the grammar |
| 404 | unknown object, tag or commit |
| 422 | resolution fails on a served commit, a label collision for instance, or a candidate regex that does not compile or exceeds its deadline |

## Examples

```bash
curl -s http://127.0.0.1:5173/api/v1/refs?kind=group | jq '.items[].key'
curl -s http://127.0.0.1:5173/api/v1/refs/piighost/fr/latest/resolved | jq '.labels[] | {label, pattern}'
curl -s "http://127.0.0.1:5173/api/v1/refs/piighost/fr-default/latest/pipeline.toml?memory=redis" -o pipeline.toml
```

## What is counted

The catalog counts its own usage, and the shape of the storage is the safeguard
rather than discipline. This is not a request log with columns removed: it is a
table of counters, aggregated as it is written.

- The finest resolution is the hour. No row corresponds to one request, so there
  is nothing to correlate.
- The columns are the shape of the call: its kind, the registry object it named,
  whether the reference was pinned, whether the caller was a browser or the
  library, and the status. No address, ever; no user agent string, no session,
  no body.
- A write is `INSERT ... ON CONFLICT DO UPDATE SET count = count + 1`, so two
  identical calls in the same hour are indistinguishable by construction.

Counting happens in memory and drains on a timer, so the hot path is a
dictionary increment: a slow disk never delays a response. The file lives at
`HUB_USAGE_DB`, a volume in production.

The library fetches `pipeline.toml` when it resolves a `catalog:` reference (in
`catalogs`, through `load_pipeline`, `RegexDetector.from_catalog` or
`piighost.catalog.pull`), so that path is what counts as a pull, apart from merely reading an object's metadata.
